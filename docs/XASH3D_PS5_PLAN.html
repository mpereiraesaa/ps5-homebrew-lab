BSP viewer with noclip

done · 2026-09-06Validated the renderer against a real map instead of a checkerboard.
Result. c1a0 renders with base textures and lightmaps and can be flown through with the physical DualSense. Gate 2 recorded 2,018 translating frames and 678 looking frames; Gate 5 completed an unattended 60,000-frame textured soak with zero errors.

Bake offline, upload on console

A host tool parses BSP v30 and emits one binary bundle: vertex buffer, index buffer, draw table sorted by texture, RGBA8 texture set, lightmap atlas, spawn point from the entities lump. The runtime only uploads and draws. Parsing bugs stay on the PC, the baker is host-tested against a tiny map you compile yourself, and commercial map data is read from a private path exactly like dev.conf.

  • Faces are convex polygons via surfedges. Fan-triangulate into an index list.
  • Texture coordinates come from the texinfo s/t vectors divided by miptex size.
  • Miptex are 8-bit paletted, embedded or from WAD3. Convert to RGBA8; index 255 is transparent only for { names.
  • Lightmaps are RGB at 16 units per luxel, sized from face extents. Pack style 0 into one atlas and emit atlas UVs per vertex.
  • Convert Quake Z-up to the camera convention once, in the baker.

Renderer work this pulls forward

  • Bump allocator over direct memory for the bundle. Fence-retired pooling waits, the map is static.
  • Command buffers far larger than the current 4 KiB per slot. A map is hundreds of draws at about 30 DWORDs each.
  • Vertex layout of position plus two UV sets, replacing position plus normal.
  • T# and S# builders and a per-draw descriptor table (base texture, lightmap) pointed to by the same 32-bit user-data slot used today for the vertex SRD table.
  • Indexed draws. Fan-triangulated BSP geometry is the first consumer that needs them.
  • One pixel shader: base × lightmap × 2 for GoldSrc overbright.

  1. Flat-shaded map, color from face index, fixed camera at spawn. Proves baker, upload, indexed draw, depth.Gate: exact readback hash.

Parallel spike: own PRX modules — closed 2026-09-06

Result. Runtime loading of an application-owned PRX works on FW 12.02. Run 20260906T085730845Z on title PPSA99999: sceKernelLoadStartModule, four exports resolved and called, a kernel import executed from module code, sceKernelStopUnloadModule, gap-free BYE. Evidence archived under research/gpu/captures/runtime/.

The converter (ps5-native-tool link --module, branch exp/prx-module of the boilerplate fork) produces the module from an lld shared object. Two loader contracts were established by bisection over about twenty launches, one variable each, and are enforced by the converter with host tests:

  • DT_PLTGOT must be a three-entry table: the loader writes entries 1 and 2 even without a PLT. A one-entry GOT with the module parameters behind it is corrupted before validation and rejected with 0x80020063.
  • e_entry is executed as the start routine and must return 0. The converter turns the layout filler into xor eax,eax; ret and points the entry at module_start when exported.

Two platform facts change the design rather than the tooling:

  • The process loader does not bind a DT_NEEDED application module at start; only platform-known sce_module entries such as libc.prx load that way. Application modules load at runtime.
  • sceKernelDlsym returns 0x80020003 for every application module, including the boilerplate's libc.prx, whatever the hash table holds, and the loader does not invoke module_start by lookup. Each module therefore carries a static, relocated export descriptor (magic PRXDESC1) that the host finds by scanning the segments from sceKernelGetModuleInfo. This is the validated resolution path.

Static linking is no longer the fallback for the engine's own libraries. The open question left for later is Sony's own DT_HASH key, which is not SysV over any obvious string; it only matters if kernel dlsym is ever needed.

Resource foundation

done · 2026-09-06Generalized the Phase 1 renderer into reusable resource contracts.
Result. The same map streams camera constants every frame and displays a pulsing green debug overlay. Run 20260906T130036578Z completed 60,000 frames with exact fence plus VideoOut retirement, intact guards, two reusable transient slots, four persistent allocations reclaimed and zero errors. The operator confirmed the pulse live.
  1. Fence-retired pool allocator over direct memory, replacing bump allocation and every hard-coded arena offset.
  2. Per-frame transient ring for dynamic vertices, indices and constants, retired by the same fence and token pair as the frame slots.
  3. Descriptor layer: V#, T#, S# builders host-tested against public PAL layouts; descriptor tables allocated from the ring and checked by the GPU-span guard.
  4. Constant buffers via V# for anything beyond the 24 direct user-data DWORDs.
  5. Shader permutation build: one table, N pipelines, metadata per pipeline. Start with two entries so the tooling is proven before Phase 4 needs a dozen.
  6. Memory model written once: CPU write then GPU read needs cache flush plus an acquire that invalidates texture and GL2 caches; GPU write then CPU read uses the existing release path. Every later phase cites this page.Gate: a host test encodes the barrier sequence.

The final overlay keeps its six indices and color constant in transient memory but generates four screen-space positions from gl_VertexIndex. An isolated hardware pass showed zero-filled structured vertex fetch for this pipeline combination; the constant-buffer V# path is the hardware-proven fallback, not an undocumented assumption.

Rules that carry through every phase

  • One variable per hardware iteration. Host gates green before the console is touched.
  • A zero submit return proves nothing. Require effect, fence, exact VideoOut token, intact guards and clean teardown.
  • Every pointer that enters a packet passes the GPU-span guard.
  • Any change to synchronization, memory layout or command emission ends with a soak before it is called done.
  • Commercial map, WAD and model data never enters a repository or an archive. Bakers read it from a private path.
  • Every hardware run is archived with artifact hash and manifest, including the ones that fail.
  • New work lives in exp/<topic> worktrees of the public repo, never in copied stages.
  • Telemetry stays on ps5log/1 over TCP. No console log files.
